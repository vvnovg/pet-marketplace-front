# Личный кабинет, часть 1: каркас, профиль, подписки

Дата: 2026-07-26
Статус: утверждён

## Задача

Страница `/[locale]/dashboard` — заглушка: шесть кнопок, ведущих на несуществующие
маршруты, и подпись «Появится в следующих фазах». Надо превратить кабинет в
работающий раздел.

Полный объём (шесть разделов) разбит на три под-проекта. Этот документ описывает
**только первый**.

### Карта под-проектов

| № | Содержание | Статус |
|---|---|---|
| 1 | Каркас кабинета, обзорная страница, профиль, подписки | этот спек |
| 2 | Мои объявления (CRUD, фотографии, статусы) + `GET /listings/my` в бэкенде | позже |
| 3 | Бронирования (действия, отзывы) + сообщения (чат, вложения) | позже |

Каждый под-проект получает свой спек, план и ветку.

## Что уже есть

- Бэкенд: `GET/PUT /users/me`, `POST /users/me/avatar`, `GET/POST/DELETE /subscriptions`,
  `GET /messages` (диалоги с `unreadCount`), `GET /favorites`.
- Фронтенд: типы DTO в `src/types/api.ts`, `apiGet/apiPut/apiUpload` в
  `src/lib/api/client.ts`, `useSession`, `FiltersPanel` каталога, примитивы
  `EmptyState`/`StatusBadge`/`Pagination`, тосты sonner.
- Guard: middleware требует `pmp_access` для `/dashboard`.

## Изменения в бэкенде

`PUT /users/me` сейчас принимает только поля сущности `Profile` (`bio`, `country`,
`city`, `address`, координаты). Имя, фамилия и телефон лежат в `User` и через API
не редактируются.

1. `ProfileUpdateRequest` дополняется тремя полями с валидацией, скопированной из
   `RegisterRequest`: `@Size(max = 100) String firstName`, `@Size(max = 100) String lastName`,
   `@Size(max = 20) String phone`.
2. `ProfileService.updateCurrentProfile` присваивает их в `User` и сохраняет через
   `userRepository`. MapStruct-маппер `updateProfileFromRequest` целится в `Profile`
   и новые поля игнорирует (`unmappedSourcePolicy` по умолчанию `IGNORE`) — присваивание
   пишем руками в сервисе.
3. Уникальности у `users.phone` нет ни в схеме, ни в репозитории — дополнительных
   проверок не вводим.
4. Схема БД не меняется: колонки `first_name`, `last_name`, `phone` уже есть в
   `001-init-schema.yaml`. Liquibase-миграция не нужна.

Семантика остаётся PUT-заменой: `updateProfileFromRequest` не использует
`NullValuePropertyMappingStrategy.IGNORE`, поэтому `null` в запросе обнуляет поле.
Форма всегда отправляет полный набор полей, так что поведение предсказуемо.

Тест: интеграционный в `src/test/java/.../user/` — `PUT /users/me` с новыми полями
возвращает обновлённые `firstName`/`lastName`/`phone`, и они сохраняются между
запросами.

## Каркас кабинета

Новый `src/app/[locale]/(dashboard)/layout.tsx` (`"use client"`) с компонентом
`DashboardNav` (`src/components/dashboard/DashboardNav.tsx`).

- Десктоп (`md` и выше): сайдбар слева фиксированной ширины, контент справа.
- Мобильные: горизонтальная лента вкладок с прокруткой над контентом.
- Активный пункт определяется через `usePathname()` из `@/i18n` — он возвращает путь
  **без** префикса локали. Совпадение точное для `/dashboard` и по префиксу для
  вложенных маршрутов.
- Все `href` — **голые** пути (`/dashboard/profile`), локаль подставляет `Link` из
  `@/i18n`.

Пункты меню:

| Пункт | href | Видимость |
|---|---|---|
| Обзор | `/dashboard` | всегда |
| Профиль | `/dashboard/profile` | всегда |
| Мои объявления | `/dashboard/listings` | `role ∈ {SELLER, ADMIN}` |
| Бронирования | `/dashboard/bookings` | всегда |
| Сообщения | `/dashboard/messages` | всегда |
| Избранное | `/favorites` | всегда |
| Подписки | `/dashboard/subscriptions` | всегда |

«Избранное» ведёт на существующую страницу `/[locale]/favorites` — она остаётся на
месте, дублировать её в кабинете не будем. Страница лежит вне route-группы
`(dashboard)`, поэтому сайдбар там не рендерится и подсветкой активного пункта этот
случай не покрывается: переход по нему уводит из кабинета. Это принятый компромисс
ради отсутствия дублирующего кода.

«Мои объявления» и «Бронирования» на момент этого под-проекта ведут на ещё не
созданные маршруты. Чтобы не отдавать 404, для них создаются страницы-заглушки с
`EmptyState` и текстом «раздел в разработке»; под-проекты 2 и 3 заменяют их
содержимым. Маршрута `/dashboard/messages` это тоже касается.

Guard не меняется: middleware проверяет наличие `pmp_access`, layout дополнительно
читает `useSession()` и не рендерит меню, пока `user` не загружен.

## Обзорная страница `/dashboard`

Заменяет текущую заглушку.

1. **Карточка пользователя**: аватар (или инициалы, как в `UserMenu`), имя + фамилия
   с фолбэком на email, бейдж роли, рейтинг и число отзывов, если `totalReviews > 0`.
   Данные берутся из `useSession()` — дополнительного запроса нет.
2. **Сетка карточек-ссылок** на разделы. Карточка показывает счётчик, если он
   доступен:
   - Избранное — `listFavorites().length` (запрос `["favorites"]`, уже используется
     на `/favorites`, кэш переиспользуется).
   - Сообщения — сумма `unreadCount` по диалогам из `getConversations()`.
   - Мои объявления — счётчика нет (нужен `GET /listings/my` из под-проекта 2).
   - Бронирования — счётчика нет (нужен фильтр по статусу, под-проект 3).

   Карточка без счётчика — обычная ссылка с заголовком и описанием, без пустого места
   под число и без надписей «скоро».

Оба запроса выполняются независимо; ошибка любого из них гасит только его счётчик
(карточка деградирует до ссылки без числа), страница не падает. Пока запрос идёт,
на месте счётчика — скелетон.

Новый эндпоинт для диалогов: `getConversations()` в
`src/lib/api/endpoints/messages.ts`. Под-проект 3 расширит этот файл остальными
операциями чата.

## Профиль `/dashboard/profile`

Клиентская страница из двух независимых блоков.

**Блок аватара.** Превью текущего `avatarUrl` (или инициалы), `<input type="file">`
с `accept="image/*"`, мутация `uploadAvatar(file)` → `apiUpload("users/me/avatar", file)`.
Бэкенд ограничивает размер 5 МБ — проверяем это на клиенте до отправки и показываем
локальную ошибку, чтобы не гонять большой файл впустую. Успех инвалидирует
`["session"]` и показывает тост.

**Форма профиля.** react-hook-form + zod по образцу auth-форм; схема
`profileSchema` в `src/lib/validation/profile-schemas.ts` зеркалит Bean Validation
бэкенда:

| Поле | Ограничение |
|---|---|
| `firstName` | `max 100`, необязательное |
| `lastName` | `max 100`, необязательное |
| `phone` | `max 20`, необязательное |
| `bio` | `max 2000`, необязательное, `<textarea>` |
| `country` | `max 100`, необязательное |
| `city` | `max 100`, необязательное |
| `address` | `max 255`, необязательное |

Координаты (`latitude`/`longitude`) в форму не выводим: в UI им нет применения, а
бэкенд принимает их как необязательные. Значение при отправке — `null`, что стирает
ранее сохранённые координаты; демо-данные их не заполняют, поэтому потерь нет.

Пустая строка в необязательном поле отправляется как `null`, а не `""`.

Начальные значения — из `useSession()`; форма перезаполняется через проп `values`
хука `useForm`, когда сессия догружается. Успех: `qc.invalidateQueries(["session"])` + тост. Ошибка
`ApiError` с `violations[]` раскладывается в `form.setError(field, { message })`,
остальные ошибки — тост с `detail`.

Новый файл `src/lib/api/endpoints/profile.ts`: `updateProfile(body)` → `apiPut("users/me", body)`,
`uploadAvatar(file)` → `apiUpload("users/me/avatar", file)`.

## Подписки `/dashboard/subscriptions`

Подписка — сохранённый набор фильтров каталога. API умеет только список, создание и
удаление; редактирования нет, поле `active` менять нечем.

**Список.** Карточки с:
- человекочитаемым описанием фильтров: название категории, породы, город, диапазон
  цены, пол, возраст, отметки о прививках и документах — только заполненные поля,
  через `·`. Названия категории и породы резолвятся из уже кэшированных
  `["catalog", "categories", locale]` / `["catalog", "breeds", …]`; если название не
  найдено, показываем плейсхолдер вместо UUID;
- датой создания;
- ссылкой «Открыть в каталоге» — собирает query-string `/catalog` из сохранённых
  фильтров теми же именами параметров, что читает страница каталога;
- кнопкой удаления с подтверждением в `Dialog`.

Пустой список — `EmptyState` с кнопкой создания.

**Создание.** Диалог с `FiltersPanel` внутри. Панель уже принимает
`filters`/`onChange`/`onReset` и типизирована как `ListingSearchParams`, так что
переиспользуется без правок. Поля сортировки и пагинации (`sortBy`, `sortDirection`,
`page`, `size`) в подписку не передаются — бэкенд их не принимает.
Поля `hasVaccination`/`hasDocuments` есть в `SubscriptionCreateRequest`, но их нет в
`FiltersPanel`; в этом под-проекте они не выставляются и всегда уходят как `null`.

Создание пустой подписки (все фильтры не заданы) запрещаем на клиенте — кнопка
неактивна, пока не задан хотя бы один фильтр.

**Кнопка «Сохранить поиск» на `/catalog`.** Постит текущие фильтры страницы,
предварительно отбросив `sortBy`/`sortDirection`/`page`/`size`. Видна только
авторизованным (`useSession()`), после успеха — тост со ссылкой на
`/dashboard/subscriptions`. Дубликаты не проверяем: бэкенд их не запрещает, а
клиентская дедупликация по набору фильтров — лишняя сложность.

Новый файл `src/lib/api/endpoints/subscriptions.ts`: `listSubscriptions()`,
`createSubscription(body)`, `deleteSubscription(id)`. Мутации инвалидируют
`["subscriptions"]`.

## Типы

В `src/types/api.ts`:

- `Subscription.isActive` → `active`. Бэкенд отдаёт `SubscriptionResponse` с
  record-компонентом `active`, Jackson пишет ключ `active`; текущее поле `isActive`
  всегда `undefined`. Поле нигде не используется, поэтому правка безопасна.
- `Subscription.filters` уточняется с `Record<string, unknown>` до структуры
  `SubscriptionFilters` бэкенда: `categoryId`, `breedId`, `city`, `minPrice`,
  `maxPrice`, `gender`, `minAge`, `maxAge`, `hasVaccination`, `hasDocuments` —
  все nullable.
- Добавляются `ProfileUpdate` (поля формы профиля) и `SubscriptionCreate`
  (поля `SubscriptionCreateRequest`).

## Обработка ошибок

Единая схема, уже принятая в проекте:

- `ApiError` с `violations[]` → `form.setError` по полям.
- Прочие `ApiError` → тост с `detail`, форма остаётся заполненной.
- 401 обрабатывается глобальным перехватчиком в `SessionProvider` — локально его не
  ловим.
- Ошибки запросов на обзорной странице деградируют карточку до ссылки без счётчика.

## Границы

Не входит в этот под-проект:

- CRUD объявлений, загрузка их фотографий, смена статуса — под-проект 2.
- Действия над бронированиями, создание отзывов, чат — под-проект 3.
- Перенос `/favorites` в кабинет — остаётся отдельной страницей.
- Смена пароля и email: у бэкенда нет соответствующих эндпоинтов.
- Переключение `active` у подписки и её редактирование: API не поддерживает.
- Заглушка `GET /users/{id}/listings` в `UserService` (возвращает пустую страницу) —
  чинится в под-проекте 2 вместе с витриной продавца.
